Getting started

The authoring kit turns your DAAD source into a folder you copy straight onto an SD card. It compiles the database, converts your artwork and audio, stages the interpreter beside them, and can launch an emulator (CSpect, or jNext) on the result. There is nothing to assemble by hand.

What you need

The kit runs on Windows and on Linux. The build scripts, the compiler and the picture converter ship in the kit; the emulator, the music converters, ffmpeg and the assembler are third-party downloads. Pick your platform below, then read Already have some of these?.

On either platform, keep the kit folder on a local drive: NTFS on Windows; ext4, btrfs or xfs on Linux. A FAT or exFAT USB stick, a network share or a Docker bind mount cannot keep the precise file times the incremental build relies on, and the build refuses to run there.

Windows setup

Windows 10 or 11. Windows PowerShell, which is part of Windows, runs the build; nothing else needs installing for a text-only game.

The interpreter, nextdaad.nex, and the DAAD compiler, NDRC, as lib\ndrc.exe, are in the kit. Gfx2Next and the video encoder are too. Download the rest and extract each into the kit's tools\ folder at the path shown:

Tool Provides Extract into Needed
Arkos Tracker 3 SongToAky.exe, SongToSoundEffects.exe, SongToYm.exe tools\ArkosTracker3\tools\ only with .aks audio
CSpect emulator, to play the result without hardware tools\CSpect\ to run the build
jNext optional second emulator that also plays cutscenes and streamed sound tools\jnext\ to run the build in jNext
ffmpeg reads your video sources tools\ffmpeg\ only when encoding an .mp4 cutscene
sjasmplus Z80 assembler tools\sjasmplus\ only to rebuild an extern with EXTERNS.BAT

tools\README.txt lists the download addresses and the exact executable paths the build checks for.

Double-click BUILD.BAT to build, RUN.BAT to play the result in CSpect (or jNext, see EMULATOR), CLEAN.BAT to start over. DEBUG.BAT builds and plays the game in the debugger. On a fresh kit the first build makes the starter game; read Where your files go before you start your own.

Linux setup

x86_64 Linux with glibc 2.34 or newer: Ubuntu 22.04, Debian 12, Fedora 36 and later. Follow the steps below in order, in a terminal. First the programs the later steps use:

sudo apt install unzip wget ca-certificates

Then install PowerShell 7.4 or newer (pwsh), which runs the build scripts. Microsoft publishes packages for every major distribution: https://learn.microsoft.com/powershell/scripting/install/installing-powershell-on-linux

Unzip the kit into its own folder and go into it. Every command from here on runs in that folder:

unzip NextDAAD-AuthoringKit-<version>-linux.zip -d NextDAAD-AuthoringKit
cd NextDAAD-AuthoringKit

The interpreter, the compiler (lib/ndrc) and Gfx2Next (tools/gfx2next/gfx2next) ship in the Linux kit. A tool that is on your PATH is found without any setting; a tool under tools/ is found there; a setting in CONFIG.local.BAT points anywhere else (see Configuration). Install only the optional tools your game uses:

  • Arkos Tracker 3 Linux release from https://www.julien-nevo.com/arkostracker/, for .aks music only. Extract the Arkos zip into tools/: its own top folder is ArkosTracker3/, giving tools/ArkosTracker3/tools/SongToAky. Or set ARKOSDIR.
  • ffmpeg from your distribution (sudo apt install ffmpeg), for video cutscenes and MUSIC PCM intros only.
  • CSpect Linux build from https://mdf200.itch.io/cspect plus mono (sudo apt install mono-devel), to play the result. Extract into tools/CSpect/; run.sh starts it as mono CSpect.exe, or set CSPECTCMD in CONFIG.local.BAT to run it some other way (Linux only, ignored on Windows).
  • jNext, optional, runs natively on Linux (no mono). See Running in jNext.
  • sjasmplus, only to rebuild an extern with externs.sh: a distribution package where one exists (sudo apt install sjasmplus on Debian), otherwise build it from https://github.com/z00m128/sjasmplus.
  • Python 3.10 or newer with Pillow and numpy, for video cutscenes only, in a virtual environment - see below.

Debian and Ubuntu do not allow pip to install into the system Python, and python3 -m venv needs the python3-venv package, so create a virtual environment once, from inside the kit folder:

sudo apt install python3 python3-venv
python3 -m venv ~/nextdaad-venv
~/nextdaad-venv/bin/pip install -r lib/requirements.txt
. ~/nextdaad-venv/bin/activate      # optional: only to run python3 yourself

lib/requirements.txt pins the Pillow and numpy versions the kit is tested with. The scripts find ~/nextdaad-venv on their own, so activating it is optional; a python3 on your PATH that already has the packages is used first.

The video tuning window (./vidtune.sh) also needs PySide6. Install it into the same venv, from inside the kit folder:

~/nextdaad-venv/bin/pip install -r lib/requirements-vidtune.txt

A minimal install may lack the system libraries Qt needs; on Debian and Ubuntu, add them with:

sudo apt install libgl1 libegl1 libxkbcommon0 libfontconfig1 libdbus-1-3 libglib2.0-0

Then build and play:

chmod +x build.sh run.sh clean.sh externs.sh vidtune.sh debug.sh lib/ndrc tools/gfx2next/gfx2next   # only if your unzip dropped the execute bits
./build.sh
./run.sh

The shipped CONFIG.BAT has RUN=1, so until CSpect is installed each build ends with ERROR: CSpect not found after the build succeeds; set RUN=0 in CONFIG.local.BAT to build without an emulator.

On a fresh kit the first build makes the starter game; read Where your files go before you start your own.

build.sh, run.sh, clean.sh, externs.sh, vidtune.sh and debug.sh are the Linux names of the six .BAT launchers and take the same arguments.

Two things differ from Windows:

  • File names are case-sensitive. Use the names this manual shows: IMAGES/, AUDIO/, VIDEO/, 001.png, STARTER.DSF, FONT.CHR. An #include or #incbin in your source must match the file's case exactly and use / between folders.
  • CONFIG.BAT keeps its name, and so does CONFIG.local.BAT. They are plain settings files of SET NAME=value lines that the scripts read; nothing executes them. Paths in them may use /.

Already have some of these?

Arkos Tracker, CSpect and ffmpeg are general-purpose tools you may well have installed already, and there is no need for a second copy. There is a directory setting per tool - ARKOSDIR, CSPECTDIR, FFMPEGDIR, GFXDIR, SJASMPLUSDIR, JNEXTDIR - and each one you set in CONFIG.local.BAT is used instead of the folder under TOOLSDIR. Anything you leave blank still comes from TOOLSDIR, so mixing the two is fine: keep the small stuff in tools\ and point the big installs wherever they already are. Absolute paths, including ones with spaces, are fine:

SET CSPECTDIR=C:\Emulators\CSpect
SET ARKOSDIR=C:\Program Files\Arkos Tracker 3
SET FFMPEGDIR=/usr/bin

Point each at the folder the tool was installed into. Arkos Tracker and ffmpeg keep their programs in a subfolder (tools\ and bin\); either the install root or that subfolder is accepted. If you keep every tool somewhere else, point TOOLSDIR at that folder instead.

Learning DAAD itself

This manual covers what is specific to the Next: the kit, the build, and how each condact behaves on this target. It does not teach the DAAD language. For that:

  • The DAAD Ready manual covers the DSF source format, the condact set, the system flags and the symbol tables. It is the go-to reference to write your adventure against.
  • The original DAAD manual is in the Docs folder of the DAAD project (or a hardcopy is available here), it is the fuller treatment of the language, worth reading once you know your way around the DAAD Ready manual.

The kit compiles your DSF with its own bundled NDRC (Next DAAD Reborn Compiler). If a CONFIG.local.BAT from an older kit still sets DAADDIR or DRCDIR, it is safe to delete those lines - neither setting is read any more since it migrated from DRC to NDRC.

Setting up an editor

Any text editor can write a .DSF file, but a few tools make the job easier:

  • VS Code is a good general-purpose editor for DAAD source - free, cross-platform, and with an extension marketplace covering the two tools below.
  • DAAD-DSF is a VS Code extension for the DSF source format: syntax highlighting for the condact set, messages and object definitions, plus checking that flags potential compiler and structural problems before you run a build. Install it from Github releases page in the repository above.
  • git tracks changes to your source as you write it, giving you a history to fall back on and, if you keep it on GitHub or similar, a backup off your own machine. In VS Code's terminal type git init initialise the tracking.

None of this is required - the build only reads the files described below, however they were written.

For a step-by-step tutorial on setting up a dev environment, please see the condact.xyz website.

Where your files go

Each game lives in its own folder inside the kit folder, called its game folder. The folder and the game's source file share one name: the game MYGAME is MYGAME\MYGAME.DSF. One kit can hold any number of games side by side, and you tell the build which one to work on (see Choosing the game).

The kit ships one game folder, STARTER\, holding the starter game. On a fresh kit with nothing configured, BUILD.BAT builds it and runs it, so you can check your setup before you write anything.

Copy STARTER\ before you write your game. Every kit update replaces STARTER\ completely, so anything you change inside it is lost at the next update. To start from the starter game, copy it to a game folder of your own first, then edit and build the copy, never STARTER\STARTER.DSF itself. While STARTER\ is the game being built, the build reminds you of this every time:

WARNING: STARTER\ is replaced by every kit update - copy it to your own game folder before writing a game (see Getting started).

The build still succeeds. A game folder named STARTER is always treated as the shipped starter - the warning prints and vidtune will not save there - so give your own game any other name.

Everything the build reads for a game is inside its game folder:

  • <GAME>.DSF - your adventure. Files it #includes or #incbins are looked up inside the game folder too.
  • <GAME>.CFG - this game's own settings (see Configuration). Optional.
  • IMAGES\ - location pictures as 001.png, 002.png and so on, plus DAAD.png for a title screen. See Graphics for the art rules.
  • AUDIO\ - Arkos .aks music and effects, and .wav samples. See Audio.
  • VIDEO\ - cutscene sources as 001.mp4 or 001.mkv (or a pre-encoded 001.vid). See Video.
  • Ready-made files in the game folder itself - a FONT.CHR custom font (see Fonts) or a POINTER.SPR mouse pointer (see Mouse), or already-converted title art. These are copied through untouched.
  • INTRO.TXT, HINTS.TXT, GAME.XBN, PART2\ to PART9\ - a loader intro, hints and other externs, and the extra parts of a multi-part game, when your game has them.

A pure-text game needs only its .DSF. Graphics, audio and video are all optional and the build skips whatever is absent. A game folder is self-contained: the build never looks in the kit folder or in another game folder for a file your game is missing, so a new game cannot pick up the starter's pictures or tunes by accident.

Everything else in the kit folder - the launchers, CONFIG.BAT, lib\, docs\, externs\, tools\ and the rest - belongs to the kit. Updating the kit lists what an update replaces.

Starting a new game

  1. Copy the STARTER\ folder to a new folder named after your game, say MYGAME\. In the copy, rename STARTER.DSF to MYGAME.DSF, STARTER.CFG to MYGAME.CFG, AUDIO\STARTER.aks to AUDIO\MYGAME.aks and AUDIO\STARTER_FX.aks to AUDIO\MYGAME_FX.aks. The build takes a game's music and sound effects from the .aks files named after the game, so without the last two renames the copy builds with no music and no sound effects.
  2. Copy CONFIG.local.BAT.sample in the kit folder to CONFIG.local.BAT, open it, and add the line SET GAME=MYGAME.
  3. Put your game's own settings in MYGAME\MYGAME.CFG. Leave the kit's CONFIG.BAT alone.
  4. Edit MYGAME\MYGAME.DSF and build it with BUILD.BAT. Do not edit the files in STARTER\.

The starter's pictures, audio and video come along in the copy. Keep what you want and delete or replace the rest. MYGAME.CFG holds VIDOPTS_001 and VIDOPTS_002 lines tuned for the starter's two demo clips; delete them when you replace those clips with your own.

Choosing the game

Name the game to build in CONFIG.local.BAT, one SET GAME= line per game you have, with all but one turned off by REM:

REM SET GAME=MYGAME1
SET GAME=MYGAME2

To switch games, move the REM. GAME is the name of the game folder (and of the .DSF inside it), with no extension.

When GAME is blank, the build looks for something it can pick without being told:

  • if the kit folder itself holds exactly one .DSF, it builds that game in the old single-game layout (see Updating the kit);
  • otherwise, if the kit folder holds no loose .DSF and exactly one game folder exists, it builds that one - on a fresh kit that is STARTER\;
  • otherwise it stops with set GAME in CONFIG.local.BAT.

So once you have copied the starter to your own folder there are two game folders, and you need the SET GAME= line. The folders PART2\ to PART9\ hold the extra parts of a multi-part game and are never taken for game folders.

Configuration

CONFIG.BAT in the kit folder holds every setting with its default value and a note on what it does. It belongs to the kit and every update replaces it, so do not edit it. Change a setting by copying its line into one of the two files below and editing the copy:

  • <GAME>\<GAME>.CFG - settings that belong to one game: COLS, COMPRESS, the video options, and so on. Each game keeps its own, so two games never share settings by accident.
  • CONFIG.local.BAT in the kit folder - settings that belong to your machine, such as tool folders and RUN, plus the GAME selector. Create it from CONFIG.local.BAT.sample the first time.

Your own game's .CFG and CONFIG.local.BAT are never shipped with the kit (only the starter's STARTER.CFG is), so an update never touches them. Both use the same SET NAME=value lines as CONFIG.BAT, and a line starting REM is ignored, so a line copies between the three files unchanged. The build only reads these files; it never runs them.

The settings:

Setting Meaning
GAME The game to build: the name of its game folder. Set it in CONFIG.local.BAT. Blank = pick one automatically, see Choosing the game.
COMPRESS 1 = ZX0-compress pictures (smaller files); 0 = raw.
RUN 1 = launch the emulator chosen by EMULATOR after a successful build; 0 = build only.
EMULATOR The emulator RUN launches: cspect (blank means this) or jnext. See Running in jNext.
COLS Text columns your game is authored for. Blank = 80 (the default), or 40 for the double-width 40-column mode. Sets the compiler's -cols option - the interpreter still boots at 80, so a 40-column game must issue GFX 1 18 in its init process. See Graphics.
TOOLSDIR Folder holding the tools above. Default tools.
GFXDIR, ARKOSDIR, CSPECTDIR, FFMPEGDIR Where each individual tool lives. Blank means "the folder under TOOLSDIR", so leave them alone for the simple layout and set only the ones you keep elsewhere. See What you need.
JNEXTDIR The folder holding jnext.exe, only for EMULATOR=jnext. Blank means tools\jnext\; on Linux, blank finds jnext on your PATH.

Local overrides. The build reads three files in turn, and a later file wins:

  1. CONFIG.BAT - the kit's defaults.
  2. <GAME>\<GAME>.CFG - the selected game's own settings.
  3. CONFIG.local.BAT - your machine's settings.

Every key works the same way: the last file to set it wins, and an empty SET NAME= clears the value. A line in CONFIG.BAT is masked while the same key is set in either of the other two. GAME is the one exception - a game's own .CFG cannot choose a different game, so a GAME line there is ignored, with a warning naming the file.

Copy only the lines you change. Never copy the whole of CONFIG.BAT into CONFIG.local.BAT or a .CFG. A full copy pins every default - the compiler version, file names, tool folders - and from then on hides any change a kit update makes to them.

vidtune saves its per-video VIDOPTS_NNN settings in the game's <GAME>.CFG, so each game keeps its own tuning and kit updates keep it. See Video.

Build and run

  • BUILD.BAT (Linux: ./build.sh) - compiles the database, converts graphics and audio, encodes any new video, copies the interpreter, and launches the emulator if RUN=1. It finishes with BUILD OK: RELEASE\MYGAME\ is ready - copy the contents of RELEASE\ to the root of an SD card, naming your game.
  • RUN.BAT (./run.sh) - launches the emulator chosen by EMULATOR (CSpect unless you say otherwise) on the game already built in RELEASE\<GAME>\, without rebuilding. CSpect sees that folder as its SD card, the same shape as the folder you copy to a real card; jNext gets a card image with the game added, see Running in jNext.
  • CLEAN.BAT (./clean.sh) - empties RELEASE\<GAME>\ for the selected game only; other games' output is left alone. It also deletes CACHE\jnext\, the jNext card copy. The next build then converts everything from scratch.
  • DEBUG.BAT (./debug.sh) - builds the game as BUILD.BAT does, also writing the source maps the debugger reads, then starts CSpect with the debugger attached. It needs CSpect 4.0 or later and EMULATOR=cspect; RELEASE\<GAME>\ is the same as BUILD.BAT makes. See Debugger.

All four work on the game GAME selects (see Choosing the game). Each launcher is a few lines that start the matching script in lib\ (build.ps1, run.ps1, clean.ps1, debug.ps1); the build itself is the same code on both platforms.

The build stops at the first error, with a message naming the cause.

Pictures, sprite sets, sounds, tunes and video are only converted or copied when their source has changed since the last build. Everything else in RELEASE\<GAME>\ is left as it is, so a game with hundreds of pictures rebuilds in seconds. A file counts as changed when its size or modified time differs, including a file replaced by an older copy. Updating the kit or a conversion tool also converts everything again. The build deletes the output of any picture or tune you remove from the game folder, so nothing lingers on the card from an earlier build.

Your database is compiled as DAAD version 3. If you are bringing in a game written for version 2, three behaviours change silently - see DAAD V3.

Running in jNext

jNext is an optional second emulator. CSpect cannot play video cutscenes and stops a long streamed sound after about a second and a half; jNext plays both. CSpect stays the default.

  1. Download jNext 1.1.87 or later from https://github.com/jorgegv/jnext/releases. On Windows, extract the x64 zip into tools\jnext\. On Linux, install the .deb or .rpm package, which puts jnext on your PATH. A Flatpak install is untested and may not see the kit's folders; if you use one, add SET JNEXT=<launcher> to CONFIG.local.BAT.
  2. Start jNext once by itself and let it download its SD-card image (about 1 GB, kept in .jnext\sdcard\ in your home folder). Close it again.
  3. Add SET EMULATOR=jnext to CONFIG.local.BAT.

From then on RUN.BAT (and a RUN=1 build) copies that card image to CACHE\jnext\card.img, adds your game to the copy, and boots NextZXOS, which starts the game. It takes a few seconds longer than CSpect. Your own copy of the card is never changed. The copy, about 1 GB, stays in CACHE\jnext\ between runs until CLEAN.BAT removes that folder.

  • Saves made in jNext are lost on the next RUN, because every run starts from a fresh copy of the card.
  • Close jNext before the next RUN; the kit will not start it twice.
  • A jNext run is still an emulator. Check cutscenes and sound on a real Next before you release.

What comes out

Each game builds into its own folder, RELEASE\<GAME>\. Copy the contents of RELEASE\ (not the RELEASE folder itself) to the root of the SD card, and each game arrives in a folder of its own. A built game holds exactly two things:

  • <GAME>.NEX - the file you launch.
  • DATA\ - everything else the game reads.

Without a loader intro, <GAME>.NEX is the interpreter itself. With one, <GAME>.NEX is the intro launcher, and the interpreter it starts is DATA\nextdaad.nex. Launch <GAME>.NEX either way.

DATA\ holds:

  • GAME.DDB - your compiled adventure.
  • 0.XMB - external message text, if your game uses XMESSAGE or XMES. It must stay beside GAME.DDB; without it those messages silently print nothing.
  • NNN.NX2 / NNN.NXI - converted location pictures, NNN.NX3 for a positioned picture, and DAAD.NX2 / DAAD.NXI for a title screen (with a .zx0 suffix when COMPRESS=1).
  • GAME.AKY, NNN.AKY, NNN.AYS, GAME.SFB, NNN.WAV - converted and copied audio.
  • NNN.VID - encoded cutscenes.
  • FONT.CHR, POINTER.SPR - your custom font and pointer, if you supplied them.
  • GAME.XBN, GAME.HNT - externs and hints, if your game has them.
  • nextdaad.nex and INTRO\ - the interpreter and the intro's own files, only when the game has a loader intro.
  • PART2\ to PART9\ and GAME2.DDB onwards - the extra parts of a multi-part game.

DATA\ is also where the game writes while it is played: save games, and the files externs keep, such as GAME.HPR (hint progress), GAME.HST (high scores) and TRANS.TXT (a transcript), all land in <GAME>\DATA\ on the card.

Games built by kits before v0.12.0 put every file loose at the card root. The interpreter still runs a game laid out that way.

The starter game

STARTER\ ships with the kit, holding STARTER.DSF along with example graphics, audio and video, so a first build works before you have written anything. It shows the Next-specific condacts in use - PICTURE/DISPLAY for location art, SFX for music and effects, BEEP for tones, GFX for cutscenes. Try the verbs MUSIC, MUTE, TUNE, BLEEP, ZAP, SAMPLE, MOVIE and REEL. To build on it, copy it first - see Starting a new game.

over the NXV player's ... ceiling The clip is too big or too long to play. The message names the longest clip your shape and frame rate allow.

The jNext card-write error ends with the code jNext gave back:

  • exit 1 - jNext is older than 1.1.87. Update jNext.
  • exit 2 - jNext could not read a file it was asked to add. Close any program holding the file; antivirus software scanning a new file is a common cause. Run again.
  • exit 3 - a file or folder name in your game folder cannot be stored on an SD card, or two names differ only in capitals. Rename it.
  • exit 4 - the file already exists on the card. Run CLEAN.BAT and run again.
  • exit 5 - the card copy in CACHE\jnext\ is damaged or could not be written. Run CLEAN.BAT, check there is free disk space, and run again.
  • exit 6 - the card is full. Your game folder is too big for it.

Warnings are different from errors. Anything about the sound-effects bank, or about picture transparency, is advisory - the build carries on and the game still ships.

When the game will not start

A build that finished can still fail on the card. These are the interpreter's own messages. Each one paints a magenta bar right across the top row of the screen and prints itself into it in white, so it is legible whatever the game had drawn - and it appears in a release build as readily as a debug one. All of them stop the interpreter; reset or power-cycle to try again.

Message What to do
NextDAAD: DDB missing - E1 There is no GAME.DDB beside the interpreter, or the card could not be read at all. The interpreter looks in the DATA\ folder next to the <GAME>.NEX you launched, so keep the game's folder whole: copy the contents of RELEASE\ to the card root, which puts <GAME>.NEX and its DATA\ together in the game's own folder.
NextDAAD: DDB oversize - E2 GAME.DDB is larger than the interpreter will load. See Limits.
NextDAAD: DDB bad header - E3 The file is there but is not a database this build can load - a truncated or corrupted copy, most often. Rebuild and copy it again.
NextDAAD: DDB wrong machine - E4 GAME.DDB is a perfectly good database, but it was compiled for a different computer - CPC, C64, MSX, PC or another. Recompile it for the Spectrum: the kit's own build already does, so this normally means a .DDB arrived from somewhere else. Spanish and English databases are both fine; it is the machine that is wrong, not the language.
NextDAAD: RUNTIME ERROR - E<n> The engine hit a fault while running your game. The digit names it: 1 is an invalid location and 4 a nested DOALL, both covered in Known differences and Platform notes; 5 is a version 3 opcode in a version 2 database, see DAAD V3.
NextDAAD: RD STACK - E9 The text reader ran out of nesting depth. This should not happen with a database this kit compiled - if it does, it is worth reporting.

Once a build runs, the game itself may still behave differently from how it did on another DAAD interpreter. Platform notes is the place to look first.

Updating the kit

To update, unzip the new kit over your existing kit folder and let it replace files. Moving up from v0.11.x or earlier is the one exception: see Moving from v0.11 to v0.12.0 below.

An update replaces the kit's own files and leaves yours alone.

Replaced by every update (the kit's files):

  • CONFIG.BAT and CONFIG.local.BAT.sample
  • the launchers: BUILD.BAT, RUN.BAT, CLEAN.BAT, EXTERNS.BAT, VIDTUNE.BAT, DEBUG.BAT (Linux: build.sh, run.sh, clean.sh, externs.sh, vidtune.sh, debug.sh)
  • the folders lib\, docs\, externs\ and .agents\
  • AGENTS.md, README.txt, NEXTDAAD.SYM, xbn.inc, xbnmod.inc
  • nextdaad.nex and intro.nex
  • tools\gfx2next\ and tools\vidtools\
  • STARTER\, the starter game

Never shipped, so never touched (your files):

  • CONFIG.local.BAT
  • every game folder of your own, including any extern module sources you keep inside it
  • RELEASE\
  • the other tools you installed under tools\ (Arkos Tracker, CSpect, ffmpeg, sjasmplus)

Where your settings belong:

Setting File
A game's own settings (COLS, COMPRESS, intro and video options, VIDOPTS_NNN) <GAME>\<GAME>.CFG
Machine settings (TOOLSDIR, tool folders, RUN) and the GAME selector CONFIG.local.BAT
Nothing CONFIG.BAT - the update replaces it

Do not edit anything in STARTER\: copy it (see Starting a new game).

A game still in the old layout. A game whose .DSF sits loose in the kit folder, as every game did before v0.12.0, still builds. But its pictures, audio and other files sit in the kit folder too, among the kit's own files, and any setting you changed in CONFIG.BAT is lost at the next update. The safe course is to move the game into a game folder of its own, and any VIDOPTS_NNN lines into its .CFG, before you rely on updates - the steps below do exactly that.

The build also warns when RELEASE\ still holds loose files from a build made by an older kit:

WARNING: RELEASE\ holds 12 item(s) from an older kit build (001.NX2, 002.NX2, 003.NX2, FONT.CHR, GAME.AKY and 7 more) - delete them; each game now builds into RELEASE\MYGAME\

The build never deletes them for you. Delete them yourself, so they do not end up on your card.

Moving from v0.11 to v0.12.0

Do this one update into a new, empty folder, not over the old kit. Unzipped over a v0.11 kit, v0.12.0 would leave the old starter files (STARTER.DSF, IMAGES\ and the rest) loose in the kit folder, and with GAME blank a loose .DSF makes the build use the old layout.

  1. Unzip v0.12.0 into a new folder beside your old kit.
  2. In the new kit folder, make a folder named after your game, matching its .DSF - for MYGAME.DSF, make MYGAME\. From the old kit folder, copy into it: the .DSF and any source files it includes, IMAGES\, AUDIO\, VIDEO\, INTRO.TXT, HINTS.TXT, the DAAD.* title files, the FONT* and POINTER* files, GAME.XBN, and any PART2\ to PART9\ folders. Copy only the ones your game has.
  3. Compare your old CONFIG.BAT with the CONFIG.BAT from the v0.11 kit zip as it was shipped (re-download the v0.11 kit zip from the releases page if you no longer have it), and copy across only the lines you changed. Game settings (COLS, COMPRESS, intro and video options) go into a new MYGAME\MYGAME.CFG. Machine settings (TOOLSDIR, the tool folders, RUN) go into a new CONFIG.local.BAT, made from CONFIG.local.BAT.sample. The v0.11 CONFIG.BAT shipped VIDOPTS_001 and VIDOPTS_002 lines for the starter's demo clips; leave those behind unless your game uses them.
  4. From your old CONFIG.local.BAT, if you had one: the VIDOPTS_NNN lines go into MYGAME\MYGAME.CFG, and machine settings go into the new CONFIG.local.BAT. Then add SET GAME=MYGAME to the new CONFIG.local.BAT.
  5. Copy across the tools you installed under the old kit's tools\ folder (Arkos Tracker, CSpect, ffmpeg, sjasmplus), unless they live somewhere else and CONFIG.local.BAT points at them.
  6. Build. The video encode cache is kept in VIDEO\ beside your clips (NNN.vid with its NNN.vid.args), so it moved with VIDEO\ in step 2: your cutscenes do not re-encode, as long as the VIDOPTS_NNN lines you moved give the same encoder settings.
  7. On the SD card, delete your game's old loose files from the card root, then copy the new MYGAME\ folder from RELEASE\. Save games made with the old layout go into MYGAME\DATA\ to stay loadable.
  8. Once the new kit builds and runs your game, you can retire the old kit folder.

If you would rather keep your game in the old layout, do step 2 without the game folder: copy the same loose game files straight into the new kit folder. Skip steps 3 and 4 and keep every setting you changed in CONFIG.local.BAT, the one settings file an update leaves alone. It still builds, but moving the game into its own folder is the better choice.
